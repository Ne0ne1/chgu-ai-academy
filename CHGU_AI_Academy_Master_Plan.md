# CHGU AI Academy — master plan разработки

Версия: 1.0 · 8 ноября 2026

## 0. Цель и правила работы

Создать полноценный по ширине пользовательских сценариев, но честный по глубине MVP образовательной платформы CHGU AI Academy: адаптивная школа AI Engineering на 12 месяцев, рассчитанная на студентов ЧГУ. В интерфейсе присутствуют главная страница, диагностика, каталог курсов, содержание модуля, качественный урок, интерактивная практика, AI Mentor, прогресс, AI Laboratory и описание годовой программы. На первом этапе **не** заявлять готовыми год материалов, трудоустройство, локальную LLM, кафедру или реальную лабораторию.

**Разделение труда:** Codex — главный архитектор, UX/UI, составление интеграционных контрактов, критический код экранов и приемка. Cursor — исполнитель изолированных задач, шаблонных модулей, хранения данных, API-провайдеров, тестов, наполнение контента в согласованной схеме и документация. Codex должен выдавать готовый промпт для Cursor при каждой достаточно самостоятельной задаче и не тратить свои лимиты на однообразную работу.

**Принцип экономии токенов:** сначала краткое исследование репозитория, затем изменения по файлам. Не перечитывать подряд весь код, не делать бесконечных косметических итераций, не писать отчёты на десятки страниц. Каждый этап заканчивается коротким фактическим статусом.

## 1. Продукт

**Кому:** студентам ЧГУ с нулевым, базовым и промежуточным опытом программирования.

**Обещание:** за 12 месяцев интенсивной практической подготовки (ориентир 15–20 часов в неделю) дать базу Python, математики, DS, ML, DL, LLM Engineering, MLOps и проектной работы для портфолио и возможного выхода на junior/стажерский уровень. Это целевой ориентир, не гарантия трудоустройства.

**Продуктовая петля:** диагностика → рекомендация → урок → задача → объективная проверка → подсказка/разбор → новое упражнение → оценка освоения → следующий шаг.

**Принципы:** методика важнее чата; AI Mentor контекстный, но не заменяет проверку заданий; содержание организовано заранее и проверяется; прогресс считается из реальных событий; доступность и мобильная версия обязательны.

## 2. UX / дизайн-система

- Прототип по ясности навигации: Яндекс Лицей / современная LMS, без буквального копирования.
- Стиль: очень светлый фон, тёмно-графитовый текст, один глубокий синий акцент, нейтральные границы, умеренные радиусы, без стекломорфизма/градиентных героев.
- Шрифт: Geist или Inter; заголовки 26–36px, текст урока 16–18px, line-height ~1.6; контент урока шириной примерно 720–780px.
- Навигация: компактный header «Главная · Программа · Прогресс · AI Laboratory», профиль / деморежим; контекстные breadcrumbs.
- Главная: одна явная «Продолжить»; прогресс, краткая программа, AI Mentor как полезное действие.
- Программа: раскрываемые модули → темы → уроки; статусы «готово/изучается/доступно/планируется».
- Урок: читаемый учебный документ, компактное sticky-содержание, AI Mentor как доступная боковая панель или drawer; на мобильных не перекрывает материал.
- Практика: условие слева, Monaco справа, проверка и вывод снизу; мобильный стек.
- Дизайн-система: Button, Card, Progress, Breadcrumbs, ModuleAccordion, LessonToc, CodeEditor, MentorPanel, FeedbackPanel, EmptyState, Skeleton.
- Доступность: клавиатура, контраст, фокус, aria labels, reduced motion.

## 4. Учебная траектория на 12 месяцев

Ориентир: 48 учебных недель, 15–20 часов/неделю, 720–960 часов. Часть этапов перекрывается; диагностика допускает пропуск освоенного без формального запрета.

| Месяц | Модуль | Итоговый артефакт |
|---|---|---|
| 1–2 | Python, Git, алгоритмы, основы SQL/API | Консольный проект и небольшой Python-сервис |
| 3 | Линейная алгебра, вероятность, статистика, NumPy/pandas | Анализ набора данных с воспроизводимым notebook |
| 4–5 | Классический ML, метрики, кросс-валидация, утечки, интерпретация | ML-пайплайн с честной оценкой качества |
| 6–7 | PyTorch, нейронные сети, CV, основы NLP | Обученная модель + отчёт об эксперименте |
| 8–9 | Transformers, embeddings, RAG, агенты, LLM evaluation | AI-приложение с тестовым набором вопросов |
| 10 | FastAPI, Docker, деплой, мониторинг, безопасность | Развёрнутый демосервис |
| 11–12 | AI Laboratory + capstone, документация и защита | Портфолио и проект под задачу университета |

**Требования к качеству урока:** измеримые цели, prerequisite, объяснение, примеры, активная проверка, задачи с проверяемыми условиями, объяснение типичных ошибок, критерии mastery, список источников.

## 6. Архитектура и поэтапная эволюция

**Стадия A — фронтенд-демо:** Next.js App Router, TypeScript, Tailwind, shadcn/ui, Lucide, typed mock fixtures, клиентское сохранение прогресса. Полноценная маршрутизация, качественные страницы, реальные кликабельные элементы. Никаких фальшивых проверок или LLM; если функция отсутствует, показывать честный статус.

**Стадия B — Cursor:** типизированная модель данных, хранилище/миграции по согласованному контракту (на MVP можно localStorage/IndexedDB; PostgreSQL только по задаче), импорт учебного контента, diagnostics scoring, проверка задач, тесты. Не усложнять инфраструктуру без необходимости.

**Стадия C — AI:** Provider interface для OpenAI-compatible endpoint и/или Ollama; серверный маршрут с валидацией, ограничением контекста и rate limit. При отсутствии ключа — явно обозначенные сценарии Demo Mentor, без притворства полноценной LLM.

**Стадия D — Production Pilot:** auth и роли, Postgres, безопасная изоляция исполнения кода, журналирование без чувствительных данных, мониторинг и нагрузочное тестирование. Локальная модель ЧГУ зависит от реального GPU и числа студентов.

**Безопасность:** пользовательский Python исполнять в отдельном Worker (Pyodide) для браузерного демо либо в защищённой серверной песочнице; не выполнять произвольный Python прямо на сервере приложения. Для автоматической проверки использовать фактические тесты, а не «нажал кнопку = сдал».

## 7. Схема данных — контракт до выбора БД

Сущности: `UserProfile`, `Track`, `Module`, `Topic`, `Lesson`, `LessonSection`, `Exercise`, `TestCase`, `Attempt`, `Mastery`, `DiagnosticQuestion`, `DiagnosticResult`, `MentorSession`, `LaboratoryProject`.

Обязательные поля:

- `Lesson`: id, slug, title, summary, estimatedMinutes, difficulty, prerequisites[], objectives[], sections[], exercises[], references[].
- `Exercise`: id, lessonId, title, statement, starterCode, expectedSkillIds[], visibleTests[], hiddenTests[], hints[].
- `Attempt`: id, exerciseId, timestamp, code, testResults[], passed, timeSpentSeconds? (только если реально измерено).
- `Mastery`: skillId, state (`not_started`/`learning`/`needs_review`/`mastered`), evidenceAttemptIds[], updatedAt.

Важно: `hiddenTests` не отдавать клиенту в реальном серверном режиме; в чисто браузерном демо не обещать секретность тестов.

### Протокол передачи задачи Cursor

Когда Codex видит самостоятельную задачу, он **не выполняет её сам**, а печатает отдельный блок:

```
CURSOR TASK #NN — <название>
Цель:
Контекст проекта и существующие файлы:
Разрешено менять:
Запрещено менять:
Контракты типов и API:
Пошаговые действия:
Acceptance criteria:
Команды проверки:
Формат отчёта:
```

Задача Cursor должна быть узкой, самостоятельно проверяемой, с чётким списком файлов/папок. Cursor работает в том же репозитории, по возможности отдельной веткой `feat/cursor-...`. Не изменять одновременно одинаковые файлы без координации. Codex принимает результат Cursor по фактическому diff, `build` и сценарию, затем планирует следующий шаг.

### Шаблон отчёта Cursor

```
CURSOR REPORT #NN
Changed files:
Implemented:
Tests run and results:
Known limitations:
Commit / branch (если был):
```

## 9. Минимальный технический сценарий для конкурса

1. Открыть главную и программу 12 месяцев.
2. Запустить диагностику, увидеть рекомендованный старт.
3. Открыть урок Python, перейти по содержанию, изучить пример.
4. Перейти к практике, допустить ошибку, увидеть корректный результат проверки.
5. Открыть наставника, получить подсказку (если демо, это явно указано).
6. Исправить код, пройти тесты, увидеть обновлённый прогресс.
7. Обновить страницу, убедиться в сохранении результата.
8. Открыть AI Laboratory, объяснить путь к университетским проектам.

## 10. Важные ограничения и риски

- «12 месяцев» — проектируемая программа, а не уже написанные 12 месяцев контента.
- 15–20 ч/неделю — интенсивно: часть студентов будет проходить медленнее.
- Для локальной LLM нужны реальные GPU-ресурсы и тестирование одновременной нагрузки.
- Автоматическая оценка свободных ответов LLM может ошибаться, поэтому ключевые упражнения должны иметь проверяемые критерии.
- Материалы Harvard/MIT используют с учётом прав и лицензий; их название не равно партнёрству.
- Вакансии Junior и гарантии найма не обещать.
- Университетская кафедра — стратегическая перспектива и отдельное управленческое решение.

## 12. Что делать после первого ответа Codex

1. Запустить промпт из отдельного файла `CHGU_AI_Academy_Codex_First_Prompt.txt`.
2. Codex создаёт фронтенд-каркас и контракты, затем останавливается на конкретной границе делегирования.
3. Он выдаёт **первый готовый `CURSOR TASK #01`** на изолированную реализацию учебных fixtures / диагностики / persist, когда исходные интерфейсы уже созданы.
4. Вставить этот промпт в Cursor, дождаться результата, вернуть короткий `CURSOR REPORT` и список изменённых файлов в Codex.
5. Codex делает ревью, интеграцию и выдаёт следующую задачу Cursor.
6. Не запускать Codex и Cursor одновременно на одних и тех же файлах.
